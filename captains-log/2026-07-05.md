# Captain's Log: 2026-07-05

## The day the browser's frame buffer folk wisdom died

This session started as a "review what we've built, is there money left on the table?" pass and ended with the single biggest perceived-latency win in the project's history: **~50ms of pure browser queueing removed from the camera-to-draw path**, measured live, side by side, with receipts.

## The review

Full pass over the repo: WORK-PLAN, the June compute audit, the frame flow in ball-toss, the WGSL engine. Conclusions:

- The hard compute money has been collected. What remains, ranked: GPU anchor decode (audit Finding 3, still the biggest readback at 153KB/frame), the batched `hand_landmark_large` WGSL port (halves two-hand landmark cost), flat landmark arrays (Finding 2, ~31K objects/sec of GC pressure), WGSL subgroups for the GEMM reductions, and int8 weights via `dot4I8Packed` as the frontier item.
- Two small hot-path bugs spotted: the 16ms oversampling gate in ball-toss can randomly drop legitimate frames from a 60fps camera (dedupe on `metadata.mediaTime` instead), and `latencyMode: 'realtime'` is not a real getUserMedia constraint (should be `latency: { ideal: 0 }`). The One Euro filters are also constructed with a hardcoded 60Hz rate while the camera delivers ~30fps.
- The latency chain was mapped end to end, which set up the main event.

## The breakthrough: MSTP delivery + same-frame consume

Robert asked the question that mattered: the frame of lag the browser enforces -- is there truly any way around it? Hours of prior research with other models had ended in "not possible." It is possible. Two tricks:

1. **`MediaStreamTrackProcessor` delivery.** Frames via a `<video>` element + `requestVideoFrameCallback` are vsync-aligned AND pass through the video element's playout buffering -- the element is built for smooth movie playback, not robotics, and holds frames roughly one camera-frame interval between receipt and presentation. MSTP taps the track *before* the video element ever sees it and hands us each `VideoFrame` the moment capture produces it. This turned out to be the big one: the playout buffer was the ~30ms nobody could name.

2. **Same-frame consume.** Ball-toss stores inference results and lets the next rAF pick them up -- up to a display frame of pure queueing. Drawing inside the inference `.then()` catches the current compositor commit instead of the next one. Universal, no API required.

## The proof: demos/latency-poc/

Two pages, both driving the real library (same `HandTracker`, same WGSL workers):

- **index.html** -- one pipeline, live toggles (D = delivery, C = consume), each OFF = exactly what ball-toss does today. Both delivery sinks run simultaneously; the inactive one is a shadow, frames matched by causality (the MSTP arrival for a frame always precedes its rVFC callback), so "MSTP head-start" is a direct same-frame, same-clock comparison. `[LATENCY]` console reports every 2s.
- **versus.html** -- side by side. Two independent tracker instances on one camera stream: left = baseline (red), right = both tricks (green), per-panel capture->draw readouts. GPU contention hits both panels equally, so the delta is fair.

**Measured on the M1 Max, real camera, two hands tracked: baseline ~56-61ms capture->draw vs ~7-9ms low-latency. A ~51ms advantage, with the low-latency path running within ~1ms of raw inference time (~8ms). There is no queueing left on the input side.**

Parity verdict, stated carefully: the software path from "OS hands over the frame" to "pixels submitted for composite" is now at native-application parity. What remains is the output compositor frame (shared with normal native macOS apps -- only exclusive-fullscreen tricks beat it) and the camera's internal ~20-50ms (shared with everyone; this is what the SpellARia prediction layer is for). The predictor now only has to cover camera hardware latency, a much smaller and more predictable target.

## Browser support

- Chromium (Chrome/Edge/Brave/Arc): MSTP since 2021, main thread + workers.
- Safari (macOS + iOS): supported, **worker-only** -- which is where the production reader belongs anyway. iOS keeps working; Phase 4 intact.
- Firefox: on their roadmap (~mid-2026); falls back gracefully to rVFC = today's baseline. Nobody gets worse.
- The immediate-draw trick is pure architecture and works everywhere.

## Library changes (committed)

- `pipeline.js` `processFrame()` accepts a `VideoFrame` as well as a video element (`videoWidth || displayWidth`); the internal per-worker `VideoFrame` clones happen synchronously so callers can close their frame right after the call.
- `HandTracker.init()` takes `{ palmEngine: 'wgsl' }` so WGSL consumers never boot the ORT palm worker first. This also fixed the PoC under Vite dev, where the ORT worker's WASM fetch fails (Vite rewrites ORT's internal imports and the fetch returns HTML -- the `expected magic word 00 61 73 6d, found 3c 21 44 4f` error is literally `<!DO`).

## Gotchas discovered

- macOS Chrome does not populate rVFC `metadata.captureTime` for camera streams; the PoC falls back to `receiveTime`, which slightly understates true glass latency (misses in-camera latency).
- Occasional small negative capture->draw readings on the low-lat path are jitter around zero from the receiveTime stand-in -- itself confirmation we're at the floor.
- A "show hand overlay" checkbox was added to both PoC pages (persisted, shared via localStorage); measurements keep recording with the overlay hidden.

## The graduation path (next session)

1. Move the MSTP reader **into a worker** inside `pipeline.js` -- spec-preferred, Safari-required, and better for perf (camera -> worker -> GPU, zero main-thread hops). Keep rVFC as the feature-detected fallback.
2. Ball-toss: draw-on-result instead of waiting for `animate()` (mark dirty + immediate render, or restructure the consume path).
3. Then the motion-signature recorder / prediction layer attacks what's left (camera internal latency), from a foundation ~50ms better than where it would have started this morning.
