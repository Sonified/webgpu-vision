# Captain's Log: 2026-06-20

## Compute Optimization Audit

Started the session with a full compute optimization audit of the WebGPU Vision library API. Scanned every source file in `src/` and `engine/` looking for places where JavaScript does compute-heavy work that could live in WGSL compute shaders, Rust/WASM, or hybrid GPU+WASM pipelines.

Identified 8 findings, documented in `COMPUTE-OPTIMIZATION-AUDIT.md`:

1. **Preview readback gate** -- palm worker unconditionally copies 442KB from GPU and does NCHW-to-RGBA conversion every frame, even when nobody displays the preview
2. **Flat landmark arrays** -- pipeline allocates ~31K objects/sec for landmark data that could be flat Float32Arrays
3. **GPU anchor decode + score filter** -- 153KB GPU-to-CPU readback where only ~400 bytes of anchors matter
4. **ORT palm worker path** (demoted) -- ORT is baseline infrastructure, not an optimization target
5. **ORT landmark workers** (demoted) -- same reasoning
6. **WASM NMS** -- weighted NMS in JS, candidate for Rust/WASM
7. **WASM affine transform math** -- rotation/projection math in JS
8. **GPU-side NMS** -- full GPU pipeline, biggest lift

Important clarification mid-audit: the WGSL engine is the primary product. ORT workers are baseline infrastructure being replaced. Findings 4 and 5 were demoted accordingly, though the ORT palm worker remains runtime-selectable.

## Finding #1 Implemented: Preview Readback Gate

Gated the 442KB `copyBufferToBuffer` + `mapAsync` + NCHW-to-RGBA JS conversion behind a `wantPreview` flag. Changes:

- `src/palm-worker-wgsl.js`: only does the GPU copy and readback when `wantPreview` is true in the message
- `src/pipeline.js`: added `wantPreview` parameter to `PalmWorker.detect()`, threaded through from `HandTracker.wantPreview` (default: false)
- `demos/ball-toss/index.html`: opts in with `gpuHandTracker.wantPreview = true`

Also removed the palm preview debug canvas from ball-toss (CSS, HTML, JS) since it was dev-only, and fixed a rVFC chain restart bug where the GPU preload could start the loop before the camera was ready.

- Face mean dropped slightly: 12.7-13.0ms vs baseline 12.9-13.1ms

## The WebGPU Renderer Experiment

Asked whether switching Three.js from `WebGLRenderer` to `WebGPURenderer` could help performance. The hypothesis: a unified WebGPU path means one API, less driver overhead, potential for shared device/buffers between rendering and inference.

### Attempt 1: Wrong import path

Tried importing `WebGPURenderer` from `three/addons/renderers/webgpu/WebGPURenderer.js`. Got a 404. In Three.js r171+, the WebGPU renderer moved out of the examples/addons into a dedicated bundle at `build/three.webgpu.js`, accessed via `import * as THREE from 'three/webgpu'`.

### Attempt 2: ORT worker crash

Switched to `import * as THREE from 'three/webgpu'` with `new THREE.WebGPURenderer()` and top-level `await renderer.init()`. The ORT palm worker started crashing with `Worker crashed: undefined`. Investigated extensively:

- MIME types fine (Python server serves .mjs as text/javascript)
- ORT bundle has no bare imports affected by the importmap
- Three.js bundle doesn't probe WebGPU at import time
- WebGPU supports multiple concurrent devices

Tried deferring `renderer.init()` (no top-level await, lazy init on Start click). ORT worker still crashed. Likely a device contention issue or a side effect of the massive `three.webgpu.js` bundle (~3MB vs ~600KB for `three.module.js`).

### Attempt 3: Working but slower

Deferred renderer init to `revealSceneUI()` (only when user clicks Start, after workers already have their GPU devices). ORT crash resolved. Demo runs. But the numbers tell a clear story:

| Metric | WebGL renderer | WebGPU renderer | Delta |
|--------|---------------|-----------------|-------|
| Hand mean | 8.1-8.7ms | 8.4-9.4ms | +0.5ms worse |
| Hand p95 | 12.3-13.0ms | 13.1-15.0ms | +1.5ms worse |
| Face mean | 12.5-12.7ms | 13.3-13.8ms | +1ms worse |
| Face p95 | 14.1-15.2ms | 17.2-19.0ms | +3ms worse |

### Why WebGPU renderer is slower

The optimization hypothesis was wrong. The key insight:

**WebGL rendering and WebGPU inference use separate GPU driver scheduling paths.** They don't compete. The WebGL scene renderer stays completely out of the inference workers' way.

Switching the renderer to WebGPU puts it on the **same scheduling pipeline** as the inference workers. Now the Three.js scene rendering contends with palm detection, hand landmarks, and face landmarks for GPU queue time. Every `renderer.render()` call steals cycles from inference.

The shared-device optimization only works if the renderer and inference can share a single `GPUDevice`. But Web Workers can't share GPU devices across threads -- each worker creates its own device. So the WebGPU renderer just adds another device to the fight.

**Verdict: WebGL for rendering + WebGPU for inference is the correct architecture.** They complement each other by using separate GPU paths.

### Reverted

Changes were never committed. Working tree is clean. The experiment lives only in this log and in the conversation history.

## Lessons Learned

1. **Separate GPU API paths are a feature, not a bug.** WebGL rendering + WebGPU compute don't contend. Unifying them on WebGPU adds contention.
2. **Cross-thread device sharing is a browser API boundary.** Workers can't share `GPUDevice` objects, so the "shared device" optimization is architecturally impossible without moving rendering into a worker (OffscreenCanvas) or inference onto the main thread (defeats the purpose).
3. **The real WebGPU rendering win would require raw WebGPU rendering** (not Three.js) where the renderer shares the same device as inference -- but that means no workers, or OffscreenCanvas with explicit device sharing. Big lift, unclear payoff for this scene complexity.
